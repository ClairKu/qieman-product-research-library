00 / EXECUTIVE SUMMARY

先用一页说清：OAP 正从“接口项目”进入“经营平台”阶段

管理层只需先听清三件事：平台价值是否成立、当前卡在哪里、这次需要什么决策。

底座和规模已形成，但“能力—场景—渠道—商业结果”还没有完全闭环。

当前最重要的不是继续堆接口，而是治理好 69 条正式能力，做出可复用的 Skills / Agents， 跑通真实用户和机构场景，并让身份、授权、计量、审计、验收和收入归因进入同一套平台。

本次建议拍板 以“有效场景与经营结果”为主验收；统一治理标准；聚焦渠道；给关键工作流唯一 Owner。
建议开场话术（30 秒）

OAP 已经不是一个从零开始的接口项目。我们已有能力资产、用户和调用规模，但距离真正的平台化经营，还差统一治理、场景交付和商业闭环。今天重点汇报三件事：为什么下一阶段必须从“开放接口”升级为“经营平台”，当前做到了什么、还卡在哪里，以及需要管理层拍板的四项支持。

01 / WHY NOW

为什么做：把盈米专业能力变成 AI 时代可分发、可交付、可经营的资产

这一章不讲功能，回答“不做会失去什么、做成会得到什么”。

01

AI 入口正在重构用户路径

用户先在大模型、智能体和工作助手中提出任务，再寻找可信金融能力。只守住 App 入口，能力难以进入新的决策链路。

02

专业能力仍是“系统孤岛”

数据、投研、投顾、内容和交易运营能力分散在接口、系统与人工 SOP 中，外部 AI 无法低成本理解和稳定调用。

03

单点项目无法形成复利

每个渠道、机构和 Agent 都重复对接，会不断复制权限、文档、合规、验收和运维成本，交付速度越来越慢。

04

金融 AI 必须有统一治理

客户数据、投顾建议、内容发布与交易动作不能依赖通用 Key 和口头边界，必须可授权、可撤回、可审计、可追责。

05

把能力供给变成业务交付

市场买的不是 API，而是基金诊断、财富规划、内容生产、客服排障等可验收结果。Skills / Agents 是从工具到结果的桥。

06

建立第二增长与商业化曲线

通过平台渠道分发、机构套餐、用量计费与共建服务，让已有能力从内部成本项转化为可复用的产品资产。

能力可发现
接入可授权
交付可验收
使用可经营
这一章的一句话

OAP 的战略价值，不是多一个官网或多一批接口，而是让盈米多年沉淀的金融专业能力，能够进入新的 AI 入口，并以统一、合规、可计量的方式规模化交付。

02 / WHAT TO BUILD

要做什么：一套能力资产化、场景化交付与企业级治理平台

不要把 OAP 讲成 MCP 官网；要讲清四层如何连成一条业务链。

L1 · 能力资产层

MCP / OpenAPI

把金融数据、投研、投顾、内容和业务系统能力标准化，形成 AI 可理解的工具。

解决：能不能接
L2 · 场景交付层

Skills

封装分析框架、业务 SOP、质检规则和交付格式，让能力能稳定完成具体任务。

解决：能不能用好
L3 · 任务服务层

Agents / AI 小顾

理解目标、调用工具、组合技能、人工复核并完成任务闭环，嵌入真实业务场景。

解决：能不能交付
L4 · 治理经营层

STARGATE + OAP

统一身份、权限、发布、评测、计量、审计、渠道、套餐与生命周期。

解决：能不能规模化经营
1
统一能力台账

MCP、Skill、Agent、渠道、Owner、风险和状态同一套资产口径。

2
统一接入与授权

API Key、OAuth、Scope、Service Group、配额和有效期可配置。

3
统一发布与评测

登记、评审、测试、灰度、发布、监控、下线都有闸口和证据。

4
统一场景产品层

官网发现、AI 实验室试用、AI 小顾承接、机构方案可组合。

5
统一运营看板

从申请、激活、调用到有效场景、留资、交易、收入全漏斗。

6
统一商业化包装

开发者基础包、机构投顾包、内容运营包与共建服务。

这一章的一句话

底层 MCP 提供标准工具，中层 Skills 把工具变成稳定方法，上层 Agents 完成端到端任务，STARGATE 与 OAP 则负责把身份、权限、质量、渠道和商业结果统一治理。

04 / NEXT ROADMAP

下一步规划：先补治理和样板闭环，再做渠道与商业规模

路线图按可验收结果排，不按功能清单排；以下为建议规划，需各 Owner 确认。

0—30 天｜锁基线

统一资产、指标与 MVP

  • 完成 69 条正式能力治理清单
  • 统一用户、激活、MAU、调用、有效应用口径
  • 冻结身份、评测、发布、计量最小闭环
  • 确定种子场景、主渠道与唯一 Owner
30—90 天｜做闭环

跑通场景、渠道与机构样板

  • ≥20 个高质量种子应用，分层统计创建、发布、有效
  • 2 个主渠道各完成 1 个 L2 场景
  • 1 个机构样板完成方案、SLA 与验收矩阵
  • 运营看板能看成功率、留存、漏斗与成本
Q4｜做规模

验证增长与商业化模型

  • 至少 1 条路径达到 L3：有完整漏斗和业务结果
  • 验证订阅、用量、共建三类收费模式
  • 建立长尾清理、质量评级与合规抽检
  • 用场景使用数据反哺能力与产品优先级

未来 90 天不以“上线了多少功能”为主目标，而以“治理好多少正式能力、跑通多少有效场景、形成几条可归因的渠道和机构闭环”为验收。

05 / RETROSPECTIVE

问题回顾：当前不是缺能力，而是缺统一口径、闭环验收和经营责任

复盘要落到“症状—根因—改法”，避免只列风险或追责。

01｜数量代替结果

表现

底层路由、应用创建数、技术接入容易被当成对外能力和有效用户成效。

改法

统一“正式能力、有效应用、L2/L3 渠道、可验收收入”定义，数量分层统计。

02｜平台治理分散

表现

MCP、Skills、Agents、渠道和机构项目各自维护权限、发布与资产口径。

改法

STARGATE 与 OAP / AI 实验室使用同一资产 ID、Owner、权限、评测和审计规则。

03｜技术打通早于产品闭环

表现

渠道完成 API 接入后，真实用户是否能完成任务、是否留资与转化仍不可见。

改法

每个渠道必须用真实场景验收，并接入身份、来源、调用、结果和业务归因。

04｜商业化过度定制

表现

机构机会依赖单次方案与专项开发，难沉淀为复用产品和可预测成本。

改法

以标准场景包 + 配置项 + SLA + 验收矩阵交付，定制需求必须反哺标准资产。

05｜责任与数据断点

表现

部分工作流缺唯一 Owner、ETA 和当期证据，历史记录容易被沿用为当前状态。

改法

关键流唯一 Owner；周里程碑绑定证据链接；无当前数据就明确标“待复核”。

这一章的一句话

过去阶段完成了从 0 到 1 的能力开放，下一阶段要纠正“数量优先、治理分散、技术接入即成功”的惯性，转向以有效场景和经营结果为中心。

06 / SUPPORT & DECISIONS

需要的支持：四项管理决策 + 两类协同资源

支持必须具体到“谁拍板、拍什么、何时验收”，不能只写“希望加强协同”。

DECISION 01 确定平台主验收指标

同意以有效应用、L2/L3 渠道、场景完成率、机构验收和收入归因为主验收，不以接口或创建数量替代。

DECISION 02 统一治理标准与控制面

明确 STARGATE + OAP / AI 实验室共同承载身份、权限、发布、评测、计量、审计和生命周期。

DECISION 03 聚焦主渠道与样板场景

管理层确定 2 个 Q3 主渠道、1 个备选渠道，以及 1 个终端场景与 1 个机构场景，避免资源摊薄。

DECISION 04 为关键工作流指定唯一 Owner

能力治理、产品场景、渠道经营、机构商业化各设唯一结果负责人，并用周度里程碑验收。

RESOURCE 01 数据与技术协同

研发、数据、运维配合完成 69 条能力当前映射、调用口径拆分、统一埋点、稳定性指标和经营看板。

RESOURCE 02 业务、合规与样板客户

投顾、运营、合规、法务共同确定场景边界；商务提供 1 个可复盘的机构试点，且慢提供真实用户样本。

建议收口话术（30 秒）

这次需要的不是泛泛的资源投入，而是四个明确决策：主指标、统一治理、渠道聚焦和唯一 Owner。只要这四件事拍板，团队就能把现有能力资产转化为 90 天内可验收的场景、渠道与机构闭环。
