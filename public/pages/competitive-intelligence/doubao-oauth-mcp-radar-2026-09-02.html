Executive verdict一个前门，三种成熟度

近一月真正的变量不是“又多了几个 MCP”，而是产品入口、协议能力和企业治理出现了不同步。营销叙事已经跨产品统一，底层授权还没有。

Protocol realityOAuth 到底支持了没有？

答案不能用一个“是”或“否”概括。必须把客户端表面、传输方式、认证发现、动态注册和令牌刷新逐层验收。

最容易犯的错

看到“连接应用”“跳转登录”“授权成功”就认定 MCP OAuth 已跑通。

登录弹窗 ≠ MCP 客户端完成 OAuth 元数据发现、PKCE、回调、令牌刷新与撤销。

已证实

  • TRAE CLI：SSE MCP 可发起浏览器 OAuth，并引用 RFC 8414 / RFC 7591。
  • TraeCode CN：截至 8/10 不支持直接浏览器 OAuth，只能 Headers。
  • 豆包工作台：自定义 MCP 可填 URL 和 Headers；第三方示例使用 Bearer Token。

仍未证实

  • 豆包工作台是否对任意远程 MCP 支持 OAuth 2.1 + PKCE。
  • 是否支持 refresh token、按资源 audience、撤销和多账号切换。
  • 手机助手 MCP 的授权主体、scope、合作方白名单与审核机制。

一条合格的 OAuth MCP 验收链

01 发现资源读取 Protected Resource Metadata，不靠人工粘贴隐式约定。
02 发现授权端定位授权服务器、端点与支持的能力。
03 PKCE 授权浏览器明确同意 scope，回调绑定客户端。
04 资源绑定access token 只对指定 MCP resource 有效。
05 刷新与撤销可刷新、可退出、可审计、可单端撤销。
协议基线：2026-07-28 MCP 规范位于本次窗口外，仅作为判断基准；它要求 OAuth 2.0 Protected Resource Metadata，并采用 OAuth 2.1 安全措施。不能把该规范当作字节产品“本月已经实现”的证据。

Implication for Yingmi对盈米不是“接不接”，而是“怎么不被绑死”

短期需要兼容现实，长期必须坚持标准。最优策略是双通道认证、按客户端隔离凭证，并把能力验收做到产品表面级。

高风险｜把豆包当成一个客户端

豆包工作台、手机助手、TRAE CLI、TraeCode CN 的认证栈不一致。同一服务必须维护表面级兼容矩阵。

中风险｜共享一个长期 Token

Header 方案最容易上线，也最容易造成跨客户端泄露与无法独立撤销。每个客户端/用户都应独立凭证。

机会｜金融数据进入连接器市场

企查查、CRM 已证明垂直企业数据可被平台分发。盈米可优先用“只读诊断 + 明确来源”切入。

Recommended moves30 / 60 / 90 天动作

兼容层不是妥协，前提是所有降级路径都可撤销、可审计、可逐步退出。

0—30 DAYS

建立“产品表面”验收矩阵

分别实测豆包工作台、TRAE CLI、TraeCode CN、Coze；记录 transport、OAuth discovery、PKCE、refresh、revoke、错误回退和多账号行为。

31—60 DAYS

上线双通道认证

标准通道采用 Streamable HTTP + OAuth 2.1/PKCE；兼容通道只发短期、只读、单客户端 Bearer Token，设置到期与主动撤销。

61—90 DAYS

争取手机与工作台合作位

准备工具白名单、scope 表、二次确认、审计日志、隐私说明和故障降级；用“基金诊断/组合风险只读服务”作为最小合作包。

服务端现在就做

  • 发布 /.well-known/oauth-protected-resource 与授权服务器元数据。
  • 优先 Client ID Metadata Documents，避免只依赖已被新规范降级的动态注册。
  • 按工具拆分 read / write scope；写操作逐次确认。
  • 返回数据附来源、时点、口径和证据等级。

明确不做

  • 不复用一把 API Key 给所有 AI 客户端。
  • 不以授权页面、回调页面或“连接成功”文案作为验收结论。
  • 不让手机 GUI 自动化成为金融交易主路径。
  • 不把第三方厂商的 OAuth 能力嫁接为平台通用能力。
